## 1. 測試目標與範圍

保證三件事:(1) 推薦結果符合已確認的業務規則(等級過濾、夥伴技能範圍、固定成員邏輯);(2) 「計算透明可驗證」與「操作快速簡單」兩項成功標準成立;(3) 本地 SQLite 與正式 Render PostgreSQL 兩環境行為一致,且無機密外洩。

範圍:第一階段全部功能(FR-1~FR-6)與部署;涵蓋後端 API、前端介面、資料庫、資料匯入、安全性。

### 不在測試範圍內

- 打工配置(FR-7,第二階段,需求未訪談,見 Q-7)
- 傷害公式與遊戲實際數值的吻合度(公式以社群考據為準,本測試只驗證「實作與定案公式一致」,不驗證「公式與遊戲一致」)
- 手機版面(需求範圍外)、Render 平台本身的可用性、社群資料源網站的正確性
- 負載/壓力測試(使用者僅本人+朋友,無此需求)

## 2. 測試策略

| 層級 | 工具 | 涵蓋範圍 |
|------|------|----------|
| 單元測試 | pytest | `services/` 傷害計算器與推薦引擎的純函式(業務規則的主戰場);匯入腳本的解析與驗證函式 |
| 整合測試 | pytest + SQLAlchemy | 模型與遷移、記憶體快取載入、匯入腳本的交易行為 |
| API 測試 | FastAPI TestClient | 全部端點的成功與失敗情境(第 5 節) |
| 前端元件測試 | Vitest + React Testing Library | 選擇邏輯、表單驗證、載入/錯誤狀態(第 6 節) |
| 端對端測試 | 暫不建置 | 規模小,以手動驗收替代;若後續迭代頻繁再引入 Playwright |
| 手動驗收測試 | 操作清單(初學者可照做) | 完整使用流程、部署後的正式環境檢查 |

修改 `services/` 計算邏輯必須附單元測試(AGENTS.md 規定)。

## 3. 測試環境與測試資料

| 項目 | 本機環境 | 正式環境 |
|------|----------|----------|
| 資料庫 | SQLite | Render PostgreSQL |
| 啟動方式 | uvicorn --reload + Vite dev server | Render 單一服務(靜態檔+API) |
| 測試資料 | 種子資料(T-5,約 10 隻帕魯) | 正式匯入資料(P-1 完成後) |
| 執行的測試 | 單元、整合、API、元件(開發時全部在此跑) | 手動驗收+冒煙測試(TC 標「正式」者) |

**測試資料規則**:

- 自動化測試一律使用 T-5 種子資料,其設計必須涵蓋:雙屬性帕魯、`team_buff` 與 `riding` 夥伴技能、不同習得等級的技能——這是業務規則案例的前置條件
- 單元/API 測試使用獨立的暫時 SQLite 資料庫(記憶體或 tmp 檔),測試間不共享狀態
- 正式 PostgreSQL 不得用於自動化測試;正式環境只做唯讀的驗收操作
- **環境差異需特別驗證**:Alembic 遷移在兩種資料庫都要能執行(TC-019);英文搜尋大小寫行為(data-model 第 5 節:應用層統一轉小寫)在兩環境結果一致

## 5. API 測試重點(FastAPI 後端)

每個端點以 TestClient 覆蓋五類情境:

- **成功(2xx)**:正確輸入→正確資料與 `{data,meta}` 格式(TC-001~003、005)
- **驗證失敗(422)**:缺欄位、型別錯誤、超出範圍——推薦端點重點:成員數上限、等級範圍、目標格式(頭目與屬性擇一)(TC-011、012)
- **未授權(401/403)**:本系統無認證,**不適用**;若未來新增寫入端點需先補此類測試
- **找不到資源(404)**:不存在的帕魯/頭目 id(TC-004)
- **伺服器錯誤(500)**:模擬內部例外→通用繁中訊息,不洩漏堆疊與路徑(TC-013 一部分)

## 6. 前端測試重點(React)

- **畫面呈現**:帕魯清單、屬性色塊、推薦結果排序呈現;無圖片(版權決策)(TC-015)
- **使用者互動**:選取/取消固定成員、屬性篩選、拆解明細展開收合(TC-015、016)
- **表單驗證**:成員數超限時前端先擋(與後端 422 雙層);等級輸入限制(TC-011、012 前端側)
- **載入/錯誤狀態**:每個 TanStack Query 呼叫都有 loading 與 error 畫面(AGENTS.md 規定);API 失敗時顯示繁中訊息不白屏(TC-022)
- **API 串接**:推薦請求帶入正確參數;回應正確渲染(TC-005 前端側)

## 7. 資料庫測試重點

- **欄位限制**:必填、唯一(paldex_no、partner_skill.pal_id)、數值範圍(TC-020)
- **關聯完整性**:外鍵有效、CASCADE 行為(整批替換時中介表隨父清除)、一對一約束(TC-018、020)
- **資料驗證規則**:data-model 第 4 節全部規則於匯入時執行(TC-020)
- **遷移**:Alembic 在 SQLite 與 PostgreSQL 均可執行與回滾(TC-019)
- **索引**:唯一索引隨約束存在;搜尋路徑用到 name_zh 索引(規模小,以存在性檢查為主,不做效能測試)

## 8. 安全性測試

- **機密資訊**:程式碼、Git 全歷史、前端 bundle、API 回應、部署 log 中不得出現 API Key、密碼、Token、連線字串(TC-013、014);`.env.example` 不含真實值
- **認證與授權**:無會員系統,無「A 使用者不能看 B 資料」情境;守住「無公開寫入端點」——確認正式環境不存在任何寫入 API(匯入僅 CLI)
- **輸入處理**:推薦端點注入嘗試(SQL 字串、超長輸入、特殊字元、負數/極大值)一律被 Pydantic/ORM 擋下,不觸發 500(納入 TC-011、012 的變體);前端渲染帕魯名稱等資料時無 XSS(React 預設轉義,測試確認無 `dangerouslySetInnerHTML`)

## 10. 測試完成標準

第一階段視為測試完成,須全部成立:

1. 高優先級案例(TC-001~017)100% 通過
2. 中優先級案例通過率 ≥ 90%,未通過者無「阻斷/嚴重」缺陷
3. 安全性測試(第 8 節)全數通過,零機密外洩
4. 正式環境冒煙測試(TC-021)通過
5. 所有已知缺陷中無未解決的「阻斷」與「嚴重」等級
