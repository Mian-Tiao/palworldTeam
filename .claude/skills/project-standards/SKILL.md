# 專案規範建立者（Project Standards Builder）

你現在的角色是一位技術主管（Tech Lead）。你的任務是根據三份設計文件，建立讓 AI 開發代理與人類開發者都能遵守的專案規範與開發準備文件。這是設計階段與開發階段之間的橋樑——規範寫得清楚，後續每一次開發互動都不必重新解釋背景。

## 前置檢查（必要）

先讀取專案根目錄的三份文件，**全部都必須存在**：

- `doc/requirements.md`（缺少時提示先執行 `/requirements-interview`）
- `doc/architecture.md`（缺少時提示先執行 `/architecture-design`）
- `doc/data-model.md`（缺少時提示先執行 `/data-model`）

**若任一檔案不存在，立即停止執行**，明確列出缺少哪些文件與對應的前置步驟。

## 既定技術決策（不可更改）

以下決策為專案既定方針，寫入規範時直接採用，不需徵詢也不得替換：

- 後端：**FastAPI**（Python）
- 前端：**React**
- 本地開發資料庫：**SQLite**
- 正式部署：**Render.com**，正式資料庫使用 **Render PostgreSQL**

若架構文件的技術選型與上述衝突，以上述為準，並在 project-memory.md 記錄此決策覆蓋（含日期與原因），同時提醒使用者架構文件需要回頭修訂。

因為本地 SQLite、正式 PostgreSQL 的差異，規範中應要求：資料庫存取一律透過 ORM（如 SQLAlchemy），禁止使用僅單一資料庫支援的專有 SQL 語法，連線字串由環境變數提供。

## 產出文件

所有產出一律以**繁體中文**撰寫。共產出四份文件，完成後向使用者摘要各文件重點。

### 1. AGENTS.md（專案根目錄）

所有 AI 工具與開發者共同遵循的開發與協作規範。內容應涵蓋：

- **專案概述**：一段話說明專案目標，並指向 `doc/` 下的三份設計文件作為完整依據。
- **技術棧**：上述既定技術決策，含本地/正式環境的差異說明。
- **機密資訊管理（必須包含，字句要明確）**：
  - 禁止將 API Key、密碼、Token、資料庫連線字串及其他機密資訊提交至 Git 或硬編碼於程式碼中
  - 所有設定透過環境變數讀取；專案須維護 `.env.example` 列出所需變數名稱與用途說明（不含真實值）
  - `.env` 必須列入 `.gitignore`
  - 發現機密已入版控時的處置：立即更換該機密（rotate），不是只從程式碼移除
- **程式碼規範**：目錄結構約定、命名慣例、FastAPI 與 React 各自的慣例（如 Pydantic schema 與 API router 的組織方式、React 元件與 hooks 的組織方式）、資料庫透過 ORM 存取的要求。
- **開發流程**：如何啟動本地環境、如何跑測試、commit 訊息慣例、修改資料模型時需同步更新 `doc/data-model.md`。
- **AI 代理協作規則**：開發前先讀 `doc/project-memory.md` 與 `doc/todo.md`；遇到文件中「待確認事項」涵蓋的範圍不得自行決定，應向使用者確認；完成項目後更新 todo.md 狀態；做出新決策時依規則更新 project-memory.md。

規範內容應根據三份設計文件具體化（例如安全性章節的要求、資料模型的敏感欄位處理），不要寫成放諸四海皆準的空話。

### 2. CLAUDE.md（專案根目錄）

為相容 Claude 工具而建立。內容保持精簡：說明本專案規範以 `AGENTS.md` 為唯一權威來源（single source of truth），指示讀取並遵循 AGENTS.md，僅此而已——不要複製 AGENTS.md 內容，避免兩份文件日後不同步。

若專案根目錄已存在 CLAUDE.md，不要覆蓋，改為在其中加入指向 AGENTS.md 的段落。

### 3. doc/project-memory.md

記錄長期有效的專案決策、技術選型、重要限制與已確認的業務規則。初始內容從三份設計文件中萃取**已確認**的部分（待確認事項不收錄）。結構：

```markdown
# 專案記憶（Project Memory)

> 本文件記錄長期有效的專案決策。閱讀本文件即可瞭解「為什麼專案是現在這個樣子」。

## 更新規則
- 僅在以下情況更新本文件：確認新決策、修改既有決策、發現重要限制
- 每次更新必須記錄：日期、原因、影響範圍
- 不記錄日常開發細節、暫時性資訊或未確認的推測

## 技術選型
| 日期 | 決策 | 原因 | 影響範圍 |
|------|------|------|----------|

## 專案決策
| 日期 | 決策 | 原因 | 影響範圍 |
|------|------|------|----------|

## 重要限制
| 日期 | 限制 | 原因 | 影響範圍 |
|------|------|------|----------|

## 已確認的業務規則
| 日期 | 規則 | 來源 | 影響範圍 |
|------|------|------|----------|
```

### 4. doc/todo.md

讀取 `doc/architecture.md`（搭配需求規格書的功能需求與優先級），列出所有待開發項目。要求：

- 每個項目包含：狀態（Todo / In Progress / Done）、描述、對應需求編號（FR-n）、相依關係（依賴哪些項目先完成）、驗收條件、優先級（高／中／低）
- 依優先級排序，同優先級之下依相依關係排序（被依賴者在前）
- **不得把未確認需求列為可直接開發項目**：凡是涉及三份文件中「待確認事項／開放問題」的需求，單獨列在文件末尾的「待確認後才可開發」區塊，註明對應的待確認編號（Q-n），不進入主要待辦序列
- 項目粒度以「一次開發會話可完成」為原則，太大的需求拆成多個項目

結構：

```markdown
# 開發待辦清單

> 依據：doc/requirements.md、doc/architecture.md、doc/data-model.md
> 狀態說明：Todo / In Progress / Done

## 待辦項目

### [T-1] 項目名稱
- 狀態：Todo
- 優先級：高
- 對應需求：FR-1
- 相依：無（或 T-n）
- 描述：...
- 驗收條件：
  - [ ] ...

## 待確認後才可開發
| 編號 | 項目 | 待確認事項 | 來源 |
|------|------|-----------|------|
| P-1 | ... | Q-n | requirements.md |
```

## 收尾

四份文件建立完成後：

1. 檢查專案根目錄是否已有 `.gitignore`；若有但未包含 `.env`，提醒使用者補上（或直接補上並告知）；若專案尚未初始化 Git，在摘要中提醒。
2. 向使用者摘要：AGENTS.md 的關鍵規範、todo.md 的項目數與最優先項目、有多少項目卡在待確認事項，建議下一步（開始開發最優先項目，或先釐清待確認事項）。
